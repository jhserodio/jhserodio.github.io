<p>Welcome to the next deep dive of our series on Math with Rust. You can find the repository with my code here.</p><p>When we look at pure mathematics, we live in a world of perfection. In it, lines have no breaks, numbers stretch to infinity, and there is always room for one more decimal between any two values. However, when we bring this math into the real world of software engineering and system architecture, that utopia collapses.</p><p>Computers have finite memory and processors with fixed-size architectures (like 32 or 64 bits). This forces us to transform the continuous, infinite universe of mathematics into a <strong>discrete</strong> and <strong>finite</strong> world.</p><p>To understand the practical implications of this in your production code, we must first revisit some foundations and understand exactly what gets lost in translation.</p><h3>1. Mathematical Foundations</h3><p>To understand what the computer <em>cannot</em> do, we need to remember what mathematics does perfectly.</p><h4>1.1. What are Functions</h4><p>In programming, the best way to understand a pure mathematical function is to think of the concept of a <strong>pure function</strong>. A mathematical function is a strict relationship that maps a set of input arguments (the <strong>domain</strong>) to a set of return values (the <strong>codomain</strong>).</p><p>Think of a simple snippet, like fn double(x: i32) -&gt; i32 { x * 2 }. The set of all x values your system allows to be injected is the domain; all possible returns make up the codomain. In a classical mathematical function, there are no API calls, no database reads, and absolutely no side effects. The contract is inviolable: for every exact argument you provide as input, there exists one (and only one) exact value in the return.</p><h4>1.2. What are Continuous Functions</h4><figure><img alt="continuous function graphic" src="/article-images/continuous-function-curve.webp" /></figure><p>A continuous function is one that has no breaks, sudden jumps, or undefined “holes”. Bringing this to our coding reality, imagine you built a function fn calculate_temperature(time: f64) -&gt; f64.</p><p>For it to possess a mathematically <strong>continuous</strong> behavior and be well-defined, microscopic variations in the arguments must result in microscopic variations in the return. If calling calculate_temperature(1.0) returns 90.0, passing a microscopically varied argument like calculate_temperature(1.000000001) must also return a predictable, proportional value like 90.000000005.</p><p>If changing the input minimally causes the output to suddenly spike from 90 to 500 (a <strong>jump</strong>), or if for the argument 1.5 the function throws an exception because it has nothing to return (a <strong>hole</strong> where the function is undefined), it is not continuous. In the perfect continuity of mathematics, the output flows smoothly, without logical crashes or invisible steps, as the input slides across the domain.</p><h4>1.3. Infinite Numbers</h4><p>In classical mathematics, there is no upper or lower limit. You can always add +1 to the largest number you can imagine, and the number line extends forever in both directions.</p><h4>1.4. Intervals and the Density of Real Numbers</h4><p>If you take the interval between the number 1 and the number 2, how many values exist in the middle? Mathematically, the answer is: infinite. You have 1.5, 1.55, 1.555, and so on. Real numbers are “dense”, which means that between any two different real numbers, no matter how close they are, there will always be another real number.</p><h4>1.5. Step Functions (Floor and Ceiling)</h4><figure><img alt="Floor function graphic" src="/article-images/floor-function-curve.webp" /></figure><p>In pure mathematics, floor(x) and ceil(x) are classic examples of what we call <em>step functions</em>. Their mathematical purpose is to map any real number to a specific integer, effectively destroying the fractional part.</p><p>To understand them visually, think of the continuous real number line as a perfectly smooth ramp. On this ramp, you can stand at any exact decimal height, like 1.73 or 1.99. Floor and ceiling functions magically transform this smooth ramp into a concrete staircase.</p><ul><li><strong>Floor (Rounding Down):</strong> Imagine gravity suddenly pulling you down to the nearest flat step below your feet. If you are standing at 1.99 on the ramp, floor(1.99) drops you hard onto step 1. You only reach step 2 when your input is exactly 2.0.</li><li><strong>Ceiling (Rounding Up):</strong> Imagine a magnetic force pulling you up to the next available flat step above you. If your input is just slightly past the step, like 1.01, ceil(1.01) immediately snaps you up to step 2.</li></ul><p>If you plot these functions on a graph, they literally look like a set of stairs. They remain entirely flat for a whole interval of decimal values, and then violently jump to the next integer. They are the perfect mathematical tool to deliberately break continuity and create the exact “steps” that we will later need to fit infinite numbers inside a computer’s finite memory.</p><h3>2. Mathematical Abstraction in Computing</h3><p>When we step off the paper and into the transistors, reality knocks on the door. Computing is fundamentally discrete (it deals with well-defined blocks, like 0s and 1s) and, therefore, cannot represent the perfect continuity of mathematics.</p><h4>2.1. Infinity does not exist in computing</h4><p>No matter how powerful your hardware is, it has a bit limit. The concept of mathematical infinity is replaced by the concept of <strong>representation limits</strong>. A 64-bit integer has clear maximum and minimum bounds. In computing, “infinity” is just a special constant flag used to signal that the limit of that architecture has been breached.</p><h4>2.2. The limit of density in real intervals</h4><p>Because we don’t have infinite bits to represent infinite decimal places, numbers in a computer are not continuous; they make “jumps”. Between one floating-point number and the next, there is an empty space where no number can be represented by the machine.</p><h4>2.3. Discretization: Transforming Continuous into Discrete (Floor and Ceil)</h4><p>Because infinite density cannot exist in machine memory due to type size limits, we must <strong>discretize</strong> math to compute it. Discretizing means taking a perfectly continuous line and transforming it into a staircase, where only fixed steps exist.</p><p>To do this, we apply mapping functions like <strong>Floor</strong> (rounding down) and <strong>Ceil</strong> (rounding up to the roof). They take values from a dense interval and force them to collapse into singular, spaced-out points. The idea that there are infinite numbers between 1 and 2 vanishes: anything that is 1.x will be forced to become a single point. The machine survives by processing bounded blocks, but we pay the price by losing the original shape of the function.</p><pre>/// Demonstrates the destruction of density by collapsing continuous values <br>/// into discrete, representable integer steps.<br>pub fn demonstrate_discretization() {<br>    let continuous_inputs = [1.1, 1.5, 1.9, 1.9999];<br>    <br>    for x in continuous_inputs {<br>        let point_floor = x.floor(); <br>        let point_ceil = x.ceil();<br>        println!(&quot;Continuous: {} -&gt; Discrete (Floor): {}, Discrete (Ceil): {}&quot;, <br>                 x, point_floor, point_ceil);<br>    }<br>    // The infinite density was reduced to only two possible states.<br>}</pre><h4>2.4. Errors, approximation, and Binary to Decimal conversion</h4><p>Since everything must be discretized into memory blocks, we face a translation issue. We think in base 10 (decimal), but computers calculate in base 2 (binary). Many fractions that are simple in decimal (like 0.1) become infinite repeating decimals in binary (0.0001100110011…). Since the computer cannot store infinite bits, it cuts this value off, generating a precision error at the very origin of the variable assignment.</p><h4>2.5. Rounding Error</h4><p>This happens when a number with many (or infinite) digits needs to be adjusted to fit the storage limit of the IEEE 754 standard (the floating-point standard).</p><pre>/// Demonstrates the classic IEEE 754 rounding error.<br>pub fn demonstrate_rounding_error() {<br>    // 0.1 has no exact binary representation due to system discretization.<br>    let a: f64 = 0.1;<br>    let b: f64 = 0.2;<br>    let sum = a + b;<br>    <br>    // In pure math, this is true. In computing, it&#39;s false.<br>    println!(&quot;Is 0.1 + 0.2 equal to 0.3? {}&quot;, sum == 0.3);<br>    println!(&quot;Actual value in memory: {}&quot;, sum); <br>    // Output: 0.30000000000000004<br>}</pre><h4>2.6. Truncation Error</h4><p>This occurs when an infinite mathematical method (like an iterative process or a Taylor series) is intentionally interrupted before the end so the program can finish running in a reasonable time. The error is the difference between the perfect infinite series and the sum up to where we decided to stop.</p><pre>/// Approximates Euler&#39;s number &#39;e&#39;, demonstrating truncation error <br>/// by intentionally stopping an infinite series.<br>pub fn demonstrate_truncation_error(terms: usize) -&gt; f64 {<br>    let mut e_approx = 1.0;<br>    let mut factorial = 1.0;<br>    <br>    for i in 1..=terms {<br>        factorial *= i as f64;<br>        e_approx += 1.0 / factorial;<br>    }<br>    <br>    // By stopping at term &#39;N&#39;, we deliberately &quot;truncate&quot; the answer,<br>    // introducing an error compared to the true infinite result.<br>    e_approx<br>}</pre><h4>2.7. Absolute Error and Relative Error</h4><p>The <strong>Absolute Error</strong> measures the direct difference between the exact value (x) and the approximated value (x_approx). The formula is |x - x_approx|. However, an error of 1 meter is irrelevant if we are measuring the distance to the Moon, but catastrophic if we are building a microchip. That is why we use the <strong>Relative Error</strong>, which is the ratio between the absolute error and the exact value, giving us the real scale of the discretization problem.</p><pre>/// Calculates and scales the mathematical error of an approximation.<br>pub fn demonstrate_error_analysis(exact_value: f64, approx_value: f64) {<br>    let absolute_error = (exact_value - approx_value).abs();<br>    let relative_error = absolute_error / exact_value.abs();<br>    <br>    println!(&quot;Exact: {}, Approximated: {}&quot;, exact_value, approx_value);<br>    println!(&quot;Absolute Error: {}&quot;, absolute_error);<br>    println!(&quot;Relative Error: {:.4}%&quot;, relative_error * 100.0);<br>}</pre><h4>2.8. Overflow</h4><p>This happens when the result of a calculation grows beyond the upper limit supported by the data type. In Rust, overflowing an integer in debug mode causes a panic, but with floats, the system returns a special infinity value (which is not mathematical infinity, but a breached limit flag).</p><pre>/// Demonstrates breaching the upper bound of a 32-bit float.<br>pub fn demonstrate_overflow() {<br>    let max_float: f32 = f32::MAX;<br>    let overflow = max_float * 2.0;<br>    <br>    println!(&quot;After overflow: {}&quot;, overflow); <br>    // Output: inf<br>}</pre><h4>2.9. Underflow</h4><p>This is the subtle opposite of overflow. It happens when we divide a number so many times that it becomes different from zero, but so minuscule that it surpasses the machine’s capacity to track the discretized difference at the lower bound. The computer gives up and rounds it to absolute zero.</p><pre>/// Demonstrates falling through the lower bound of precision.<br>pub fn demonstrate_underflow() {<br>    let min_float: f32 = f32::MIN_POSITIVE;<br>    let underflow = min_float / 1_000_000_000.0;<br>    <br>    println!(&quot;After underflow: {:?}&quot;, underflow); <br>    // Output: 0.0 (The value fell into the discretization gap)<br>}</pre><h3>Finishing…</h3><p>When we write code, we are not dealing with perfect mathematics, but rather with a mechanical and electronic simulation of that mathematics. Understanding discretization, the lack of true density, and margins of error is fundamental when defining types in your systems. Depending on your application’s domain (financial systems, flight radars, or machine learning), you must choose the correct algorithms and data types to ensure these approximations never destroy the logical validity of your software.</p><img src="https://medium.com/_/stat?event=post.clientViewed&referrerSource=full_rss&postId=ac13946514b3" width="1" height="1" alt="">
